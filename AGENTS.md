# Project instructions

This repository is a template for a visual novel built with **Pixi’VN** and **React**. These instructions are intentionally general and can be used as they are; developers may adapt them to their game whenever useful.

## Engine

- [Pixi’VN documentation](https://pixi-vn.com/)

Consult the official Pixi’VN documentation when implementing or changing engine features.

## Project structure

Application code lives in `src/`.

- `src/assets/`: game assets such as images, audio, and video. Follow the asset manifest and loading system already in place; when adding or moving assets, update the required manifests or configuration.
- `src/components/ui/`: basic UI components generated by **shadcn**. Keep this directory for reusable base UI components; take local changes into account if regenerating or updating the components later.
- `src/components/`: all other React components, including screens, menus, dialogs, and providers.
- `src/content/`: TypeScript modules that define and register game content and elements, such as characters, labels/scenes, and related logic. Follow the registration flow configured in `vite.config.ts` and the Pixi’VN plugin files.
- `src/content/labels/`: labels (scenes) of the game, one module per label or group of related labels.
- `src/locales/`: translation files. Keep keys consistent across supported languages and add translations to the existing i18n configuration.
- `src/routes/`: game routes and screens managed by the router. Handle generated router files according to the generator configuration in the project.
- `docs/`: game documentation. This directory may initially be empty; organize its contents into subdirectories by topic, such as story and endings, objectives and missions, characters, locations, items, and minigames. Do not document assets here; manage them in their dedicated directories and manifests.
- `src/lib/`: shared supporting logic, hooks, queries, stores, and utilities. Keep code here when it is not tied to the presentation of a specific component.
- `src/models/`: shared models and types for the game domain and persisted data.

Paths may change as the template is adapted. Update this document along with the project structure if directories are moved or renamed.

## Generated files

Files with the `.gen.*` suffix are generated automatically and must not be edited by hand. VS Code settings (`.vscode/settings.json`) exclude them from the file watcher and search results and mark them read-only to reduce accidental changes. If a generated file needs a correction, find and modify the configuration, source content, or plugin that produces it, then let it regenerate.

In this project, for example, the Pixi’VN plugin in `vite.config.ts` generates `src/pixi-vn.worker.gen.ts` and `src/pixi-vn.keys.gen.ts`; TanStack Router generates `src/routeTree.gen.ts`. The asset manifests in `src/assets/` are also generated by the asset pipeline: update the assets and source configuration, not the generated manifest.

## VS Code

The `.vscode/` directory contains formatting settings, recommended extensions, tasks, and debug configurations. Tasks may install dependencies and start the Vite server when the folder is opened in VS Code. Tasks are also configured for starting and stopping the server, building, local preview, and debugging the game. Check `tasks.json`, `launch.json`, `settings.json`, and `extensions.json` before changing these workflows or starting duplicate processes.

## Working conventions

- Use English as the default language for development artifacts, including code, identifiers, comments, and project documentation. Game dialogue and player-facing text may use the languages chosen for the game.
- Reuse APIs and patterns already present in the project before introducing new dependencies or a second system for the same purpose.
- Keep game content, React presentation, routing, and shared utilities separated according to the structure above.
- Do not edit generated files manually when a source file or configuration exists to regenerate them; find and update the source instead.
- Keep translations up to date for every language supported by the game.
- Update the documentation in `docs/` when narrative or design information relevant to the team changes. Do not use it as an asset inventory.
- Before adding a library, check whether the project or Pixi’VN already provides the required functionality.

## UI

- Every screen is a **TanStack Router** route in `src/routes/`.
- For UI made of elements that are not drawings coming from media (text, buttons, layouts, menus, dialogs, forms), always use **React** (with the existing shadcn/ui components when suitable).
- For images (assets), use **PixiJS** (`pixi.js`) directly. Do not use Pixi’VN for UI: Pixi’VN is for the narrative canvas, while UI rendering with PixiJS must go through `pixi.js` itself.
- If `pixi.js` is used directly and is not yet a direct dependency of the project, add it to `package.json` first, before writing code that imports it.

## Verification and tools

Available scripts are defined in `package.json`. This template includes commands for development, builds, linting, and formatting/type checks; review the scripts before using them and choose those relevant to the change.

When available, use the **Chrome DevTools MCP server** to run or inspect the game in a browser, check console errors, and verify visible behavior. If it is unavailable, use the project’s local commands and clearly state any checks that could not be performed.

## Recommended skills

Use the Pixi’VN skills available in the working environment when relevant. Choose the skill for the area being changed: project setup, narration, characters, canvas and transitions, assets, UI, audio, storage, saves, or history.

When using `pixi.js` directly, it may be worth installing the PixiJS skills as well (and adding `pixi.js` as a dependency beforehand, see the UI section).

Skills are reference tools, not required repository dependencies; their availability varies between environments. For React, TanStack Router, Tailwind CSS, or shadcn/ui, consult dedicated documentation or skills when needed for the change; there is no need to require additional skills for the template as a whole.

## Distribution

The game is a **Tauri**-only desktop/mobile app (see `src-tauri/`). See the [Tauri documentation](https://tauri.app/) for instructions on building and publishing the project

Releases are built by `.github/workflows/desktop.yml` (Windows, macOS, Linux) and `.github/workflows/mobile.yml` (Android, iOS). Both start when a tag matching `v*` is pushed. To generate a release, create and push a tag (for example `git tag v1.0.0 && git push origin v1.0.0`); the workflows build the game with `tauri-action`/the Tauri CLI and attach the bundles to the GitHub release with that tag.

If an AI agent creates and pushes the tag, once it is pushed it must send the developer, in the chat, the link to the workflow runs and to the release (for example `https://github.com/<owner>/<repo>/actions` and `https://github.com/<owner>/<repo>/releases/tag/<tag>`, with the real owner, repository and tag; `gh run list` and `gh release view <tag> --json url` can help find them), so the developer can reach the release without searching for it.

### Signing for a real release

The packages produced by these workflows are **not signed**: Android is a debug `.apk`, iOS is built without code signing (not installable on a device), and desktop installers carry no code-signing certificate. They are fine for testing, but before a real release to players the packages must be properly signed. Follow the Tauri guides for each platform (<https://tauri.app/distribute/sign/android/>, `/ios/`, `/windows/`, `/macos/`) and keep every secret in GitHub secrets, never in the repository.

- **Android**: generate a release keystore (`keytool -genkeypair -v -keystore release.keystore -alias <alias> -keyalg RSA -keysize 2048 -validity 10000`) and keep it safe, since losing it prevents updating the app. Store the base64 of the keystore and its passwords as secrets, recreate the keystore and the signing configuration in the `build-android` job, and build with `tauri android build` instead of `--debug`.
- **iOS**: requires an enrolled Apple Developer Program account. Export the Apple Distribution certificate as `.p12`, download the matching provisioning profile, store them (base64) with the password and Team ID as secrets, remove the "disable code signing" step from the `build-ios` job, and build without `--debug`.
- **Windows**: use a code-signing certificate configured through the `bundle > windows` options of `src-tauri/tauri.conf.json`.
- **macOS**: use an Apple Developer ID certificate plus notarization (`APPLE_CERTIFICATE`, `APPLE_CERTIFICATE_PASSWORD`, `APPLE_ID`, `APPLE_PASSWORD`, `APPLE_TEAM_ID` passed as environment variables to `tauri-action`).

### Steam (Tauri + Steamworks)

> Temporary section: this Steam documentation is tied to Tauri and will probably be removed once the Roves documentation covers it. In game code, prefer the platform-agnostic `achievements` API of `@drincs/roves-api/achievements` for achievements.

> **Mobile:** Steam is not supported on iOS or Android; the feature is disabled automatically on those targets.

The multiplatform template includes a **ready-to-use Steam integration** built on [Tauri](https://tauri.app/) and the Rust crate [`steamworks`](https://crates.io/crates/steamworks) (a wrapper around the Steamworks SDK). Everything is opt-in: the feature is excluded from the build by default and adds zero overhead when unused.

#### Enabling Steam support

Edit `steam_appid.txt` in the repo root and replace the value with your real Steam App ID.  
Use `480` (Spacewar) for local testing without a published app.

`steam_appid.txt`:

```txt
480
```

Open `src-tauri/Cargo.toml` and add `steam` to the default features list:

`src-tauri/Cargo.toml`:

```toml
default = ["steam"]
```

Alternatively, pass `--features steam` to any `cargo` or `tauri build` command without touching the file.

The `steamworks` Rust crate already ships the native redistributable libraries for all platforms — **nothing to download manually**. The `build.rs` in this template copies the correct file into `src-tauri/` automatically during compilation.

##### Bundling for distribution

To include the library in the final installer you need to tell Tauri to bundle it. Create a platform-specific config file for the platform you are targeting — you only need the one(s) that apply to you:

`src-tauri/tauri.windows.conf.json`:

```json
{
    "bundle": { "resources": ["steam_api64.dll"] }
}
```

`src-tauri/tauri.macos.conf.json`:

```json
{
    "bundle": { "resources": ["libsteam_api.dylib"] }
}
```

`src-tauri/tauri.linux.conf.json`:

```json
{
    "bundle": { "resources": ["libsteam_api.so"] }
}
```

Tauri v2 merges the matching file into `tauri.conf.json` automatically at build time. Create only the files for the platforms you want to distribute on — one, two, or all three.
