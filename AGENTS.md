# Project instructions

This repository is a template for a visual novel built with **Pixi’VN** and **React**. These instructions are intentionally general and can be used as they are; developers may adapt them to their game whenever useful.

## Engine

- [Pixi’VN documentation](https://pixi-vn.com/)
- [Pixi’VN ink documentation](https://pixi-vn.com/ink/) & [Native Ink documentation](https://github.com/inkle/ink/blob/master/Documentation/WritingWithInk.md)

Consult the official Pixi’VN documentation when implementing or changing engine features.

## Project structure

Application code lives in `src/`.

- `src/assets/`: game assets such as images, audio, and video. Follow the asset manifest and loading system already in place; when adding or moving assets, update the required manifests or configuration.
- `src/components/ui/`: basic UI components generated by **shadcn**. Keep this directory for reusable base UI components; take local changes into account if regenerating or updating the components later.
- `src/components/`: all other React components, including screens, menus, dialogs, and providers.
- `src/content/`: TypeScript modules that define and register game content and elements, such as characters, labels/scenes, and related logic. Follow the registration flow configured in `vite.config.ts` and the Pixi’VN plugin files.
- `src/content/labels/`: TypeScript labels (scenes). Writing the story in Ink (`ink/`) is always preferable; use TypeScript labels only when a scene needs purely TypeScript logic or complex animations that Ink cannot express well.
- `src/content/ink/`: TypeScript extensions that connect Ink to the game code.
  - `hashtag-commands.ts`: registers custom `# command` tags (`HashtagCommands.add`). When the narration needs to run TS/JS logic, add a command here and call it from Ink with a tag (e.g. `# navigate <route>`, `# unlock achievement <id>`). Each command has a handler and a zod `validation` that defines the accepted syntax. It is also the place to centralize animations or effects that are always used the same way, so they are defined once, controlled from a single point, and triggered directly from Ink.
  - `text-replaces.ts`: registers replacements for `[placeholder]` text in Ink (`TextReplaces.add`). The placeholder is replaced by a value computed from logic or tied to a variable (e.g. a character ID becomes the character's current name). Use `type: "after-translation"` to replace after translation, and `i18nInterpolation: true` to also work inside i18n strings.
- `ink/`: Ink source files (`.ink`) containing the story, dialogue, and narrative flow. This is the preferred place to write game narration.
- `public/ink-json/`: the compiled JSON output (`*.gen.json`) of the Ink files in `ink/`. Generated, do not edit by hand; read it to verify what the system actually understood from the Ink sources.
- `src/locales/`: translation files. Keep keys consistent across supported languages and add translations to the existing i18n configuration.
- `src/routes/`: game routes and screens managed by the router. Handle generated router files according to the generator configuration in the project.
- `docs/`: game documentation. This directory may initially be empty; organize its contents into subdirectories by topic, such as story and endings, objectives and missions, characters, locations, items, and minigames. Do not document assets here; manage them in their dedicated directories and manifests.
- `src/lib/`: shared supporting logic, hooks, queries, stores, and utilities. Keep code here when it is not tied to the presentation of a specific component.
- `src/models/`: shared models and types for the game domain and persisted data.

Paths may change as the template is adapted. Update this document along with the project structure if directories are moved or renamed.

## Generated files

Files with the `.gen.*` suffix are generated automatically and must not be edited by hand. VS Code settings (`.vscode/settings.json`) exclude them from the file watcher and search results and mark them read-only to reduce accidental changes. If a generated file needs a correction, find and modify the configuration, source content, or plugin that produces it, then let it regenerate.

In this project, for example, the Pixi’VN plugin in `vite.config.ts` generates `src/pixi-vn.worker.gen.ts` and `src/pixi-vn.keys.gen.ts`; TanStack Router generates `src/routeTree.gen.ts`. The asset manifests in `src/assets/` are also generated by the asset pipeline: update the assets and source configuration, not the generated manifest.

## VS Code

The `.vscode/` directory contains formatting settings, recommended extensions, tasks, and debug configurations. Tasks may install dependencies and start the Vite server when the folder is opened in VS Code. Tasks are also configured for starting and stopping the server, building, local preview, and debugging the game, including with Roves. Check `tasks.json`, `launch.json`, `settings.json`, and `extensions.json` before changing these workflows or starting duplicate processes.

## Working conventions

- Use English as the default language for development artifacts, including code, identifiers, comments, and project documentation. Game dialogue and player-facing text may use the languages chosen for the game.
- Reuse APIs and patterns already present in the project before introducing new dependencies or a second system for the same purpose.
- Write narration and dialogue in Ink (`ink/`) by default; use TypeScript labels in `src/content/labels/` only for pure TypeScript logic or complex animations.
- Keep game content, React presentation, routing, and shared utilities separated according to the structure above.
- Do not edit generated files manually when a source file or configuration exists to regenerate them; find and update the source instead.
- Keep translations up to date for every language supported by the game.
- Update the documentation in `docs/` when narrative or design information relevant to the team changes. Do not use it as an asset inventory.
- Before adding a library, check whether the project or Pixi’VN already provides the required functionality.

## UI

- Every screen is a **TanStack Router** route in `src/routes/`.
- For UI made of elements that are not drawings coming from media (text, buttons, layouts, menus, dialogs, forms), always use **React** (with the existing shadcn/ui components when suitable).
- For images (assets), use **PixiJS** (`pixi.js`) directly. Do not use Pixi’VN for UI: Pixi’VN is for the narrative canvas, while UI rendering with PixiJS must go through `pixi.js` itself.
- If `pixi.js` is used directly and is not yet a direct dependency of the project, add it to `package.json` first, before writing code that imports it.

## Verification and tools

Available scripts are defined in `package.json`. This template includes commands for development, builds, linting, and formatting/type checks; review the scripts before using them and choose those relevant to the change.

When available, use the **Chrome DevTools MCP server** to run or inspect the game in a browser, check console errors, and verify visible behavior. If it is unavailable, use the project’s local commands and clearly state any checks that could not be performed.

## Recommended skills

Use the Pixi’VN skills available in the working environment when relevant. Choose the skill for the area being changed: project setup, narration, characters, canvas and transitions, assets, UI, audio, storage, saves, history, or Ink content (`pixi-vn-ink`). For work involving Ink, also follow any Ink setup instructions required by the relevant skills, and prefer Ink over TypeScript labels for narration.

When using `pixi.js` directly, it may be worth installing the PixiJS skills as well (and adding `pixi.js` as a dependency beforehand, see the UI section).

Skills are reference tools, not required repository dependencies; their availability varies between environments. For React, TanStack Router, Tailwind CSS, or shadcn/ui, consult dedicated documentation or skills when needed for the change; there is no need to require additional skills for the template as a whole.

## Distribution

The game is intended to be distributed through **Roves**. See the [Roves documentation](https://roves.pixi-vn.com/) for up-to-date instructions on preparing and publishing the project.

Releases are built by `.github/workflows/release.yml` (desktop, desktop + Steam, and mobile). To generate a release, create and push a tag matching `v*` (for example `git tag v1.0.0 && git push origin v1.0.0`). The workflow builds the game and attaches the bundles to the GitHub release with that tag.

If an AI agent creates and pushes the tag, once it is pushed it must send the developer, in the chat, the link to the workflow run and to the release (for example `https://github.com/<owner>/<repo>/actions` and `https://github.com/<owner>/<repo>/releases/tag/<tag>`, with the real owner, repository and tag; `gh run list` and `gh release view <tag> --json url` can help find them), so the developer can reach the release without searching for it.

### Signing for a real release

The packages produced by `release.yml` are **not signed**: Android is a debug `.apk`, iOS is an Xcode project plus an unsigned Simulator app (not installable on a device), and desktop installers carry no code-signing certificate. They are fine for testing, but before a real release to players the packages must be properly signed.

- **Android**: generate a release keystore (`keytool -genkeypair -v -keystore release.keystore -alias <alias> -keyalg RSA -keysize 2048 -validity 10000`) and keep it safe, since losing it prevents updating the app. Store `base64 -w0 release.keystore` and the passwords as GitHub secrets, then in the `android` job of `release.yml` add to the Roves step `android-release: 'true'`, `android-keystore-base64`, `android-keystore-password`, `android-key-alias`, and `android-key-password` (read from `${{ secrets.* }}`). The result is a signed release `.apk`.
- **iOS**: requires an enrolled Apple Developer Program account. Export an Apple Distribution certificate as `.p12`, download the `.mobileprovision` that matches the certificate and the app bundle ID, and store their base64 (`base64 -w0 <file>`), the `.p12` password, and the Team ID as GitHub secrets. In the `ios` job add `ios-release: 'true'`, `ios-certificate-p12-base64`, `ios-certificate-p12-password`, `ios-provisioning-profile-base64`, `ios-team-id`, and set `ios-bundle-id` and `ios-app-name`. The result is a signed `.ipa`.
- **Desktop (Windows/macOS)**: `roves-action` does not sign them. Sign the files afterwards with your own certificates (Windows code-signing certificate; Apple Developer ID plus notarization for macOS), or accept the OS security warnings.

Never commit keystores, certificates, passwords, or provisioning profiles: use GitHub secrets only. See the `roves-action` inputs in the [Roves documentation](https://roves.pixi-vn.com/docs/action) for the up-to-date list.
